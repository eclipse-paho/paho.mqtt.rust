#        persistence_sync and persist_timeout

## Where the file I/O happens (strace -f, pub1-seq --persist --n 300, tokio)
# base: one thread does 302 store opens AND 302 socket writes - the event loop
# new:  socket writes on the loop thread, 300 store opens on another (mqtt-persist).
#       The 2 opens left on the loop are the connect-time open/load, by design.

## QoS 1 throughput with file persistence, as a fraction of the same run without
# tokio seq  base 11,662/s = 43.3% of plain   new 12,834/s = 52.8%
# smol  seq  base 12,237/s = 50.5%            new 12,134/s = 45.8%
# tokio pipe base 24,629/s =  3.5%            new 28,660/s =  4.2%
# smol  pipe base 27,564/s =  2.9%            new 28,391/s =  3.4%
#
# Targets were 80% (seq) and 50% (pipe) and are missed by a long way. The store,
# not the hop, is the bottleneck: FilePersistence creates one file per message,
# about 36 us each, and persist-before-send holds the wire until it returns.
# 1/36us = 28K/s, which is what the pipelined runs measure. put_many saves the
# lock and the round trip, not the file creates.
